PART I — PROPOSED RULING (DEC-0018 CANDIDATE)
======================================================================

1. PURPOSE
Remove the chair as a per-transaction bottleneck while strengthening, not weakening, the control record. Two mechanisms ruled together: (A) delegation-by-class for rulings; (B) envelope execution with hard stop points, replacing per-action tool approval. Entry condition E1 applies to both.

2. ENTRY CONDITION
E1. Guard fixes F1/F2 applied to governance_guard.py and the deny-shaped re-probe set passes green (incl. git -C global-option prefix cases and 2>&1 redirection cases, per WS-E 72/73). Nothing in this ruling activates until E1 is evidenced on the record.

3. MECHANISM A — DELEGATION-BY-CLASS
3.1 Class A (auto-rule). Mechanical/administrative: register numbering, filename and format conformance, echo acknowledgments, retry-on-red within an already-authorised envelope. Claude (coordinator seat) rules and records; chair audits in batch.
3.2 Class B (rule-and-notify). Substantive but low-stakes choices inside a chair-ruled envelope: scenario wording within the accepted RQA spec, fixture parameters within Test Plan §8.1, implementation choices within an accepted design. Admission test: reversible-by-construction. Rationale recorded per ruling; all Class B rulings land in a daily digest draft; chair veto window open until next boot. [See Footnote F1.]
3.3 Class C (chair only, permanent). Guard deny set and permission tiers; gate criteria; register semantics; spend; M12 independence; merge to main (SO-1 untouched); exit decisions; any irreversible or system-level action (incl. elevated OS operations, e.g. the H-6 ownership repair); anything touching this ruling itself.
3.4 Tags. Every delegated ruling carries its class tag on the record.
3.5 Tripwire TW-1. If any Class B ruling is subsequently reversed by the chair, its category reverts to Class C automatically pending an explicit re-admission ruling.
3.6 Audit. M12 audits delegation usage (counts, classes, reversals, digest completeness) every cycle.

4. MECHANISM B — ENVELOPE EXECUTION WITH STOP POINTS
4.1 Envelope declaration. Every numbered prompt dispatched to CC declares: (i) writable path scope (worktree-bounded); (ii) permitted tools; (iii) expected artefacts; (iv) named stop condition. Chair (or Class A/B delegate where admitted) approves the envelope once at dispatch.
4.2 Free execution inside envelope. Within a declared envelope CC executes without per-action approval requests. Per-action tool prompts are retired for in-envelope actions.
4.3 Frozen-path deny set (guard-enforced regardless of envelope): governance_guard.py; all registers; B7_GATE.md; golden fixtures; branch-protection configuration; this ruling document. Amendable only by chair-ruled fix prompts (Class C).
4.4 Stop points. Each envelope terminates at a named checkpoint: CC halts and emits a STATUS ECHO — artefacts produced, tests green/red, register deltas staged, anomalies — and awaits release. Chair reviews state, not transactions.
4.5 Standing stop points for B7: SP-1 after guard re-probe (E1 evidence); SP-2 after M13; SP-3 before M12 launch; SP-4 after each Terminal-2 batch; SP-5 before any merge to main (SO-1 merge verification unchanged); SP-6 before first Regime 2 run; SP-7 at Regime 2 completion.
4.6 Breach handling. Any attempted write outside envelope scope or against the frozen-path set is a guard red: CC halts, records WS-E entry, awaits chair. No retry without ruling.

5. RISKS AND MITIGATIONS
R1 Scope creep in Class B — mitigated by reversibility admission test + TW-1 + M12 audit.
R2 Guard as single control after approval retirement — mitigated by E1 precedence, frozen-path set, breach-halt 4.6.
R3 Digest fatigue / rubber-stamping — mitigated by batching at boot/close only and M12 completeness check.

6. CHAIR DECISION SOUGHT
Rule DEC-0018 as above (or amended), effective on E1 evidence. On ruling: register entry DEC-0018; prompt conventions updated to carry envelope declarations and class tags.
