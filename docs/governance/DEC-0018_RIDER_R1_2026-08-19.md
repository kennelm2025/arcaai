ALLOW-AND-LOG inside a valid envelope. That mechanism is **adopted**; what was

guard. See section 3(c) of the correction file. A2.2's claim that this
"directly discharges the observability concern in WS-E 75 for the in-envelope
case" therefore holds only under the corrected mechanism, and WS-E 75's
general limit — that human surfacing of an ask is not provable by any probe —
is untouched either way.

======================================================================
AMENDMENT A1 — DEFAULT IN-ENVELOPE TOOLSET (amends §4.2)
======================================================================

A1.1 Insert after §4.2:

  "4.2a Default toolset. Unless an envelope declaration explicitly narrows it, every envelope carries the following standing toolset without per-action approval:
    (i)   file create / write / edit / delete within the declared writable path scope;
    (ii)  git add, commit, checkout/switch on feature branches, and branch creation within the worktree;
    (iii) git push to any branch OTHER than main;
    (iv)  PR creation and PR-body authoring (gh pr create or equivalent), including labels and reviewers;
    (v)   test execution, linters, and read-only repository inspection;
    (vi)  conda environment activation (arcaai) and package queries (no installs — installs remain declarable per envelope).
  A prompt may narrow this set for a given envelope; no prompt may widen it beyond the frozen-path deny set in §4.3. Omission of a toolset line in a prompt does NOT reintroduce per-action asks — the default applies."

A1.2 Explicit exclusions restated for the record (unchanged from candidate): merge to main (Class C, SP-5, SO-1 verification unchanged); pushes to main (blocked by M3 branch protection regardless); any write to the §4.3 frozen-path set; register writes outside staged-delta convention; elevated OS operations.

A1.3 Rationale. The candidate as drafted relies on each numbered prompt's per-envelope tool list. A single omitted line in a future prompt would silently reintroduce approval friction. A standing default makes the chair's intent ("only ask me to merge") structural rather than dependent on prompt-authoring discipline.

======================================================================
AMENDMENT A2 — ASK-TIER GUARD RESOLUTION INSIDE ENVELOPES (new §4.7)
======================================================================

A2.1 Insert as §4.7:

  "4.7 Ask-tier resolution. governance_guard.py rows resolve inside a valid envelope as follows:
    (a) DENY tier: unchanged. Deny is deny inside or outside an envelope. Frozen-path writes (§4.3) remain deny. Breach handling per §4.6.
    (b) ASK tier: within a valid, in-scope envelope, ask-tier actions resolve to ALLOW-AND-LOG. The guard does not halt for chair input; it records the row (action, tier, envelope ID, timestamp, resolution=ENVELOPE-ALLOW) to the ask-tier log.
    (c) Ask-tier log review is a mandatory element of every STATUS ECHO at the envelope's stop point (§4.4). The chair reviews resolved ask-tier rows in batch, not per transaction.
    (d) Outside any envelope, or where envelope scope is ambiguous, ask-tier behaviour is unchanged: halt and ask. Ambiguity resolves conservative.
    (e) Tripwire TW-2: if the chair, on stop-point review, flags any ENVELOPE-ALLOW row as wrongly resolved, that guard row's category reverts to halt-and-ask inside envelopes pending an explicit re-admission ruling. Reversals are M12-auditable alongside TW-1."

A2.2 Rationale. The F1–F4 guard work deliberately widened the ask tier (long-form branch deletes, prefix/redirection cases per WS-E 72/73/74), and WS-E 75 records the ask-tier observability gap. The candidate retires per-action APPROVAL prompts but is silent on ask-tier GUARD halts — as written the chair would still be pinged on every ask-tier row, defeating the stated intent. A2 resolves this without weakening the control: deny tier and frozen paths are untouched, every envelope-allowed row is logged and reviewed at the stop point, TW-2 gives per-row demotion symmetrical to TW-1, and M12 audits usage. This also directly discharges the observability concern in WS-E 75 for the in-envelope case: ask-tier events become a reviewed log rather than an unrecorded click.
