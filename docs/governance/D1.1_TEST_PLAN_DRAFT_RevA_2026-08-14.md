## 1. Purpose, scope, and relationship to the TOR and DEC-0015

### 1.1 What this document is

This is the D1.1 Draft Test Plan, the first deliverable of workstream WS-T1
(`TOR §4:48-52`). The TOR specifies it as authored against the repository —
reading the actual test suite, gate history and the working runner spike per
D2.2a — carrying the formal-execution governance pack as a first-class section
and implementing rulings-record amendments 1–4 and 9 (`TOR §4:49`).

It is authored fourth in the ruled sequence, after the commissioning frame, the
spec schema and the runner spike, because the sequencing is deliberately
proof-first: the panel "interrogate[s] better with a working artefact in front
of them" (`TOR §4:52`, `TOR §9:132-134`). This plan is therefore written against
a harness that has already run, not against an intention.

### 1.2 Authority: what this document is a precondition for

Regime 2 — formal execution, meaning any run intended as evidence — carries a
single stated precondition: "the Test Plan ruled ACCEPTED by the panel process,
carrying the formal-execution governance pack" (`TOR §5A:92-93`). Until that
ruling exists, no run is admissible as gate evidence, and results produced under
Regime 1 are "INADMISSIBLE as gate evidence — permanently, not merely until
ruled" (`TOR §5A:85`).

The reason the bar is permanent rather than provisional is the failure class
WS-E 63 records: a green read as meaning something it cannot mean. A promotion
path would reintroduce exactly that.

### 1.3 Who rules it

Ruling authority is split: "the operator rules the commissioning frame (D2.0)
directly; the formal-execution pack is ruled through the Test Plan panel process
(D1.4)" (`TOR §5A:101`). Panel members act as interrogators, never authors;
panel material leaves and returns hash-pinned; rulings are the operator's alone
(`CLAUDE.md`, Working protocol item 7). DEC-0015 records the same constraint
from the TOR's own panel pass: reviewer outputs are concurrence and
recommendation only, one reviewer having phrased four outcomes as rulings, which
are recorded as recommendations.

### 1.4 What this plan does not govern

- **The scenario spec schema.** D2.1 owns spec structure and is "the keystone
  artefact; everything else hangs off it" (`TOR §4:56`). Where this plan needs
  schema behaviour it references the schema and does not restate it, since two
  statements of one rule diverge.
- **The D2.0 commissioning frame**, held to one page by `amendment 8` — "it must
  not grow into a miniature Test Plan". Nothing here amends it.
- **The runner.** D2.2a and D2.2b are WS-T2 build artefacts (`TOR §4:57-58`).

- **Gate criteria.** These live in `docs/build/B7_GATE.md` and are never
  restated or extended here. §7.3 records a consequence of that boundary.

### 1.5 Relationship to DEC-0015 and the register structure

DEC-0015 is the harness's register home, discharging Ruling 1: this sits under

## 3. Retrieval scenario classes

### 3.1 The three classes

Ruled at OQ2 and closed for batch 1. Each asks a different question of the same
corpus.

| Class | The question it asks | Schema `retrieval_kind` |
|---|---|---|
| **Corpus QA** | When the corpus contains the grounding a question requires, is that material what comes back? | `corpus_qa` |
| **Citation-following** | When a document refers to another, does the retriever reach the referent? | `citation_following` |
| **Gap detection** | When the corpus does *not* contain the grounding, does the system say so rather than answer anyway? | `gap_detection` |

### 3.2 Class does not determine scoring method, and the asymmetry is deliberate

The schema carries three retrieval kinds and **two** scoring methods
(`arcaai/harness/schema/scenario_spec_v0.2.schema.json`). Corpus QA and
citation-following both score by `semantic_distance` — recall at k over an
expected grounding set. Only gap detection scores by `gap_detection`.

This is not an omission. Corpus QA and citation-following are both presence
questions and differ in how the expected set is *chosen*, not in how success is
measured: for corpus QA the expected set is the material that grounds the
question, for citation-following it is the referent of a citation. Gap detection
measures absence and needs its own formula, for the reason §4 sets out.

### 3.3 Statute retrieval — candidate class, not created at batch 1

A distinct statute-retrieval class was considered following F1, and is **not
created for batch 1**. The class set is ruled at OQ2 and closed; more
substantially, creating a scenario class to explain a single observation risks
encoding that observation as a design fact before it is understood, and the
observation comes from a permanently inadmissible run (§12).

It is recorded as a candidate. The coverage rule at §2.1 will expose whether
statute documents behave differently from synthetic narrative documents under
one similarity measure, because the rule puts both in the matrix.

## 4. Gap detection and retrieval quality are distinct claims

### 4.1 The governing rule

This plan preserves the distinction between a scenario detecting a deliberately
planted under-implementation and any general claim about retrieval quality.
D1/D2 detection evidences gap-detection capability; it does not by itself
evidence retrieval quality broadly (`amendment 2`, at
`docs/governance/RULINGS_RECORD_2026-08-10_TOR-test-capability.md:60`). The
TOR's own acceptance criterion restates it: gap-detection scenarios demonstrate
detection, or recorded non-detection with analysis, of D1 and D2 "as Regime 2
runs, evidencing gap-detection capability distinctly from general retrieval
quality" (`TOR §8:123`).

### 4.2 Why these are two claims and not one

D1 and D2 are two under-implementations planted deliberately as gap-detection
ground truth (`TOR §1:17`). A gap-detection scenario asks whether the system is
honest under absence. A corpus-QA or citation-following scenario asks whether
the retriever ranks well under presence.

A system can hold one and not the other in either direction: a retriever that
returns almost nothing scores well on abstention and badly on recall; a
retriever that always returns its top k confidently scores well on recall and
fails every planted gap. Neither result licenses an inference about the other,
because neither measurement is taken over the other's conditions.

### 4.3 The mechanical basis, already in the schema

Semantic-distance scoring is recall at k over the expected grounding set, and
the schema states that this "scores PRESENCE: how much of what should have been
retrieved was retrieved". Gap-detection scoring is a weighted combination of
abstention and distractor avoidance, neither term a semantic distance. The
schema's own sentence is the anchor: "a gap-detection scenario that scored well
on semantic distance would be measuring the opposite of what it is for".

The exclusivity is mechanical. `expected_document_ids` is "meaningless for
gap_detection, where by construction no document grounds the claim", and the
gap-detection branch forbids it outright, just as the semantic-distance branch
forbids the gap-detection scoring block. A spec cannot express a scenario that
claims both at once.

### 4.4 Consequence for evidence

A gap-detection result, run under Regime 2 and meeting its entry criteria
(`TOR §5A:99`), is citable as evidence of gap-detection capability against the
named ground truth. It is **not** citable as evidence that retrieval works. A
corpus-QA or citation-following result is citable as evidence of retrieval
quality on the query and grounding set it was run over, at its pinned snapshot —
and is **not** citable as evidence that the system abstains correctly where
grounding is absent. A gate claim spanning both requires results of both classes.

### 4.5 The failure mode this prevents

A suite that detects both planted gaps being read, at a gate or in a prospect
pack, as a general statement that retrieval works. It is attractive precisely
because it reads well: two deliberate defects found, ground truth matched,
nothing missed. But the evidence produced is entirely about behaviour under
absence — every document the scenario touches is a distractor, and by
construction no document would have been correct to retrieve.

## 5. Pass/fail criteria

### 5.1 Where a threshold lives

Per scenario, in the spec. The schema carries `acceptance` as
`{metric, operator, value}`, with the operator enumerated rather than free text
"so the gate is evaluated, not interpreted". This plan states how a threshold is
**chosen** and does not restate any number the schema carries — the same
division `amendment 3` makes for migration-diff semantics, and for the same
reason: a rule stated in two places drifts.

### 5.2 Class-level defaults, expressed as a rule

A default gives the panel something to interrogate and the scenario author a
baseline rather than a blank page. A per-scenario override is permitted and
**must carry a stated reason**.

**Semantic-distance scenarios (corpus QA, citation-following).**

The metric is recall at k over the expected grounding set E, so its granularity
is `1/|E|` and its attainable values are exactly the multiples of `1/|E|`. A
threshold that is not such a multiple is misleading: it silently rounds to the
next attainable value while reading as though it were finer.

> **Default threshold = `ceil(0.8 × |E|) / |E|`.**

Worked: at `|E| = 1` the default is 1.0; at `|E| = 2, 3, 4` it is also 1.0; at
`|E| = 5` it is 0.8; at `|E| = 8` it is 0.875. The rule is strict for small
expected sets because it is honest about them — with a small set you either
retrieve them all or you fail, and pretending otherwise by writing 0.8 against
`|E| = 2` states a criterion the metric cannot express.

**A scenario at `|E| = 1` is a binary probe, not a graded measure**, and the
plan requires it to be described as one. `top_k` is the sensitivity lever there,
not the threshold. This is the F1 observation turned into a rule rather than
left as a caution.

**Gap-detection scenarios.**

The score is `w_a·A + w_d·(1 − |R_k ∩ D|/|D|)` with `w_a + w_d = 1`, A binary.

> **Default threshold = 0.8.**

At the fixture weighting `w_a = 0.6, w_d = 0.4`, that default requires the
system to abstain *and* to admit no more than half the distractor set. Two
properties worth stating because they are not obvious from the number: any
threshold above `w_d` makes abstention **necessary** — a system that answers
confidently cannot pass however few distractors it returns; and any threshold
above `w_a` additionally constrains distractor avoidance. The weights are
therefore not presentational, and a scenario changing them changes what its
threshold means.

### 5.3 What evaluates acceptance, and where the verdict is recorded (H-8)

**H-8 was deferred to its proper stop and this is that stop**, because Regime 2
becomes live when this plan is ruled (`TOR §5A:92-93`). Ruled 2026-08-14:

> **The runner evaluates.** The verdict is written to the result artefact
> (D3.1) **and** to the D2.5 results ledger entry, and is **immutable in the
> ledger by the same mechanism that makes the regime marker immutable**.

**Grounds, recorded because the ruling binds runner design.** H-10 ruled the
run-record obligations machine-asserted under Regime 2 where they had been human
records under Regime 1; acceptance evaluation is the same shape. H-9 ruled the
regime marker mechanically immutable because "a marker a process can edit is a
promotion path" — and the pass/fail verdict is the field most likely to be
quoted away from its artefact, so the argument applies with more force, not
less. `TOR §3:32` already describes the runner as "scored/evaluated".

**Two conditions, both ruled in.**

1. **`evaluated` is always present and explicit.** An absent verdict must never
   read as a pass. This mirrors the discipline the runner already applies to an
   unpinned retrieval snapshot, where absence is reported as unpinned rather
   than passed over.
2. **An inadmissible run's verdict is marked inadmissible, never suppressed.**
   Deleting it loses the fact that a verdict was computed; marking it preserves
   the record while `TOR §5A:99` bars its use.

### 5.4 Recording rule

**A threshold, the expected-set size `|E|`, and `top_k` travel together in the
result artefact.** A threshold quoted without the other two is not
interpretable: 0.8 means different things at `|E| = 2` and `|E| = 8`, and a
recall figure without `top_k` does not say what was searched.

## 6. Data provenance rules

This section states where every byte a scenario touches comes from, how that
origin is identified, and what a result must carry for the origin to be
recoverable. Which movement in those facts invalidates which prior results is
§9.

### 6.1 Two scenario classes, two provenance lines

**Retrieval-class scenarios query the authored corpus at a pinned snapshot.**
`generator_seed` is FORBIDDEN on a retrieval-class spec, because "a seed
recorded against a run that never used one is a reproducibility claim with
nothing behind it".

**Scoring-class scenarios materialise records from the in-house synthetic
generator at a declared seed.** `generator_seed` is mandatory there, in the spec
and in the reproducibility payload (`amendment 6`). A scoring-class spec may
additionally pin a corpus snapshot; if it does, only the manifest pair is
required of it, never the retrieval-snapshot hash, "which would describe an
index the scenario never queries".

Real, non-synthetic data of any kind is out of scope for the whole capability
(`TOR §3:43`). Scenario content may be LLM-assisted at the design layer only;
all volume data is produced programmatically from versioned specs, with external
model outputs treated as distinct provenance lines, schema-validated before
pipeline entry and hash-pinned (`TOR §2:24`).

### 6.2 Corpus identity has exactly one governing artefact

`verticals/fraud/corpus/MANIFEST.yaml` is the sole governing artefact for corpus
identity, licence, SA5 classification and eligibility (`DEC-0014` item 1).
Document fields are split: **identity** — id, source, licence, SA5
classification, content hash, eligibility history — is immutable; **processing
observations** — chunker version, embedding model, chunk count, ingest timestamp
— are updatable with a manifest version change and never touch identity
(`DEC-0014` item 1).

The `corpus_version` Postgres row is evidence that a version was loaded. It is
not a reconstruction of the manifest and must never be used to regenerate one
(`DEC-0014` item 2).

### 6.3 Three hashes, three different questions

- **Manifest hash** — over the normative canonical form: deterministic UTF-8,
  stable key ordering, LF endings, insignificant whitespace removed
  (`DEC-0014` item 4). Answers *is this the same manifest content?*
- **Eligible-set hash** — over the sorted eligible document-and-content-hash
  pairs. Answers *did these runs use the same documents?* It deliberately
  excludes processing facts (`DEC-0014` item 3), and that exclusion is the point
  of having two hashes: it lets a re-chunk be recognised as *the same
  documents*, so document drift and processing drift stay separable.
- **Retrieval-snapshot hash** — the eligible pairs plus chunker version,
  embedding model and chunk count (`DEC-0014` item 3). Answers *did these runs
  retrieve from an operationally identical corpus?* Required for retrieval-class
  scenarios at spec schema v0.2.

`DEC-0014` item 3 states why they are not one hash: "conflating both into one
hash weakens both questions."

### 6.4 Known limit of the retrieval-snapshot pin

The platform's hash function stringifies absent processing facts, so the hash
computes cleanly over documents carrying no processing block. A spec can
therefore satisfy the v0.2 requirement with a correct, matching hash that folds
in absent values — a required pin with nothing behind it, which is the defect
the requirement exists to close. **Making the pin mandatory does not make the
facts present.**

**Currently latent, verified 2026-08-14:** every one of the sixteen eligible
documents in `manifest_version` 2026-08-13.8 carries a complete processing
block, so no eligible document is presently affected. The limit is real and
unclosed; it is not presently biting. That distinction is recorded so a later
reader neither dismisses the limit nor assumes it is currently corrupting
results.

### 6.5 Listed versus current snapshots

Commissioning (Regime 1) runs pin the snapshot current at run time
(`amendment 9`; `TOR §5A:88`). Formal (Regime 2) runs require the corpus at a
**listed** snapshot (`TOR §5A:94`). The asymmetry is deliberate: commissioning
proves plumbing and is permanently inadmissible, so an unlisted snapshot costs
nothing; formal execution is evidence, and evidence must cite a snapshot that
passed the governed listing act.

**Listed is not the same as eligible**, and §2.3 records a live instance:
fourteen documents are listed at `pending_review` and are invisible to the
retriever. A Regime 2 run satisfies the listed-snapshot criterion while covering
only the eligible subset, and the coverage rule at §2.1 operates over
eligibility for that reason.

### 6.6 Immutability of the source data

Authoring and listing are separate governed acts, and nothing under
`verticals/fraud/corpus/` changes outside one. Authored corpus documents are
immutable once committed: a correction is a new entry with a new hash, never an
edit, and a revised or withdrawn document is an appended eligibility transition,
never a deletion — enforced mechanically at load (`DEC-0014` item 5). Data
itself never enters git. Provenance for scoring-class inputs is therefore a
recipe — generator plus seed plus parameter ranges — not a stored file, which is
why the seed is mandatory rather than advisory.

### 6.7 What a result must carry

The reproducibility triple is mandatory on every result: spec hash + model
version + corpus snapshot, plus generator seed wherever the generator is invoked
(`TOR §5:74`; `TOR §8:124`). Corpus snapshot identity is the `DEC-0014` manifest
hash pair, with the retrieval-snapshot hash additionally required for
retrieval-class scenarios at schema v0.2. Per §5.4, the acceptance threshold,
`|E|` and `top_k` travel with it.

A result missing any leg of its triple is not a weaker result; it is an
unreproducible one, and is inadmissible under `TOR §5A:99`.

## 7. Gate linkage: harness evidence and B7 exit

### 7.1 The governing ruling

Ruling 3 (OQ3) is preferred-primary, the middle position: "Harness Regime-2 runs
against the ruled Test Plan are the preferred primary evidence for retrieval
quality and for detection of the planted D1/D2 gaps. They are not a hard
single-point dependency that can block the entire B7 gate if equivalent citable
evidence exists by another governed route"
(`docs/governance/RULINGS_RECORD_2026-08-10_TOR-test-capability.md:42`). The
operator's recorded rationale is that making the gate wholly dependent on a
brand-new harness creates a single point of failure during the harness's own
early life, while making it merely nice-to-have under-weights the capability
being built (same file, line 43).

### 7.2 What preferred-primary means operationally

**(a) First call.** Where a B7 exit item can be evidenced by a retrieval-class
scenario, the harness is the route of first resort, and the Gate Acceptance
Record cites the Regime-2 run artefact by its reproducibility triple.

**(b) Substitution is permitted and must be justified in the record.** If
harness evidence is unavailable or immature at gate close, the item may be
evidenced by another governed route. The gate record names the item, the
substitute, and why the harness route was not taken.

**(c) Equivalence test.** A substitute qualifies only if it meets, by its own
mechanism, the properties that make a Regime-2 run citable: produced under a
governed act; cited as path @ commit SHA or a CI result transcribed as text,
never a bare path and never `main` (`docs/build/B7_GATE.md` §3); reproducible or
immutable by construction; and asserting the same proposition as the scenario it
replaces, rather than a weaker one nearby.

### 7.3 Mapping to the B7 criteria as they actually read

`docs/build/B7_GATE.md` §5 carries a list headed "Not allowed — absence blocks
the gate regardless of what else landed", stating that the list "is exhaustive
as written and is the required-evidence list at §3". Its five items are quoted
verbatim and mapped; the gate document's fuller descriptions are not paraphrased
here, because a plan that paraphrases a gate's required-evidence list is how two
accounts of one requirement begin.

| B7 required item, verbatim | Harness relationship |
|---|---|
| corpus manifest with provenance, licence status, SA5 classification and time-versioned eligibility | **Not harness evidence.** A document artefact under `DEC-0014`; a run pins the snapshot, it does not evidence the fields. |
| grounding test | **Harness-primary.** Citation-following class (§3.1). |
| negative test | **Harness-primary.** |
| insufficient-evidence fallback | **Split.** The harness can evidence the behaviour; recorded reasoning behind a threshold is a document act. |
| CF-1 spot-check result | **Not harness evidence.** Conformance review, nominated at `docs/build/B7_GATE.md` §1.1. |

**Stated plainly rather than mapped over:** `docs/build/B7_GATE.md` contains no
reference to the harness, to this Test Plan, or to the D1/D2 planted
under-implementations — verified by search, whose only apparent hit is a
substring inside a correlation identifier. So although `TOR §1:17` makes D1/D2
detection part of the capability's first cargo, it is **not** a required B7 exit
item on the gate document as it currently reads. Gap-detection evidence stands
as evidence of gap-detection capability, distinct from any general claim about
retrieval quality (`amendment 2`). Adding it to B7's required list would be a
change to gate criteria, which is not this plan's to make; it is routed to the
B7-exit ruling pack.

### 7.4 The admissibility bound

Only Regime 2 runs meeting their entry criteria at ruled spec versions are
citable as gate evidence; the reproducibility triple is mandatory; and a run
with a failed or skipped pre-flight is inadmissible regardless of outcome
(`TOR §5A:99`). Regime 1 results are inadmissible permanently and cannot be
promoted (`TOR §5A:85`). Preferred-primary never softens admissibility: it
governs which admissible route is preferred, not what counts as admissible.

### 7.5 Recorded panel divergence

Reviewer B recommended a hard requirement, Regime-2 evidence mandatory with
manual notes as commentary only; Reviewer C recommended preferred-primary with
no single-point dependency; Reviewer A took no position and required this Test
Plan to make the relationship precise (rulings record, line 44). The operator
adopted C's position. This section is what satisfies Reviewer A's requirement.

### 7.6 Sufficiency

Which scenarios constitute sufficient harness evidence for a B7 exit item is
determined by the coverage rule at §2.1 and the acceptance criteria at §5.
Invalidation of prior harness evidence by corpus or model movement is §9.

## 8. The formal-execution governance pack

This is the section whose absence blocks Regime 2 (`TOR §5A:93`), and it is a
first-class section rather than an appendix by requirement (`TOR §4:49`). Seven
elements, enumerated at `TOR §5A:94-100`.

### 8.1 Entry criteria per session

All must hold (`TOR §5A:94`):

1. **Environment asserted via pre-flight.** `python scripts/d22a_preflight.py`
   exits 0 with all assertions GREEN. UNKNOWN and SKIPPED both exit non-zero and
   never collapse into green.
2. **Corpus at a listed snapshot**, post listing-act pin (`amendment 9`).
3. **Spec versions ruled** — not merely valid.
4. **Model version stated.**
5. **No unconsumed suspension in force**, per §8.3.

**Pre-flight failure fails hard** (`amendment 7`): non-zero exit immediately,
blocking all downstream steps, so no partial or corrupted ledger entry can be
written in CI or locally. A session that cannot assert its environment does not
produce a weaker result; it produces no result.

**Criteria 2 to 5 are machine-asserted under Regime 2**, per H-10, which ruled
that the three run-record obligations that were human records under Regime 1 are
asserted by the instrument under Regime 2.

### 8.2 Exit criteria per session

1. **Every scheduled scenario executed, or its non-execution recorded with a
   reason** (`TOR §5A:95`). A scenario silently absent from a results set is
   indistinguishable from one never scheduled.
2. **Results ledgered**, each entry carrying its regime marker (`TOR §4:61`),
   which is mechanically immutable per H-9 — "a marker a process can edit is a
   promotion path".
3. **Acceptance verdicts recorded** per §5.3, in the artefact and the ledger,
   immutable by the same mechanism as the marker.
4. **A summary produced.**

### 8.3 Suspension and resumption

**A session halts on** (`TOR §5A:96`): pre-flight red mid-run; environment
drift; corpus or model version change mid-session.

**Re-entry requires** a fresh pre-flight and a re-pinned reproducibility triple.
Re-entry is not resumption: the triple has been re-pinned, so results before and
after were produced under different pinned conditions and must not be presented
as one continuous set. Which prior results survive the movement that caused the
suspension is determined by §9.

A suspension is *consumed* when its re-entry conditions have been met and
recorded. An unconsumed suspension blocks session entry under §8.1 item 5.

### 8.4 Session objectives and scope

Each formal session names its scenario set and purpose **before execution**;
additions mid-session are a new session (`TOR §5A:97`).

The reason is admissibility rather than tidiness: a scenario added after results
have been seen is selected in knowledge of what the suite was already producing,
and the resulting set cannot be distinguished from one assembled to support a
conclusion. Naming the set in advance is what makes the session a test rather
than a search.

### 8.5 Defect classification and routing

At §10, which is a pack element and not a separate concern (`TOR §5A:98`).

### 8.6 Evidence admissibility

At §7.4. Two consequences worth stating because they run in the unfavourable
direction: a **passing** run with a skipped pre-flight is inadmissible, because
the conditions under which the pass was obtained were never asserted; and a
Regime 1 result that happens to be excellent is inadmissible permanently and is
re-run under Regime 2 if wanted, never promoted.

### 8.7 Re-test and regression rules

At §9, stated operationally as `amendment 1` requires.

## 9. Invalidation and re-test rules

### 9.1 The rule is leg-scoped

Movement in a pinned leg invalidates only those results whose claim depends on
that leg. The alternative — any movement invalidating everything — would discard
the separation `DEC-0014` item 3 was bought to provide, and would over-invalidate
so obviously that it would be worked around rather than followed.

### 9.2 The table

| Movement | Invalidates | Survives |
|---|---|---|
| Eligible-set hash changes | All retrieval-class results | Scoring-class results not pinned to the corpus |
| Retrieval-snapshot hash changes, eligible-set hash unchanged | All retrieval-class results — processing drift changes what the retriever sees | The same-documents claim, which the eligible-set hash still evidences |
| Manifest hash changes, both content hashes unchanged | Nothing | All results. The change is metadata-only; it is recorded, not acted on |
| Model version changes | All results produced with that model | Results at other model versions |
| Spec hash changes | That scenario's prior results | Every other scenario |

### 9.3 What must re-run

A result invalidated by a movement re-runs **under Regime 2 at the new pin**, as
a fresh session under §8.4 with its scenario set named in advance. Invalidation
does not delete the prior result: it remains in the ledger, marked, with the
movement that invalidated it recorded against it. A ledger from which
invalidated results disappear cannot show what changed.

### 9.4 A caveat that bounds row two

**Where processing facts are absent from the manifest, retrieval-snapshot
equality is not evidence of processing stability** — the hashes match because
both sides folded in the same absent values (§6.4). Results pinned over absent
processing facts cannot rely on row two of the table above.

This is stated, not ruled. It is presently latent: as of `manifest_version`
2026-08-13.8 every eligible document carries a complete processing block. It
becomes live the moment an eligible document does not, and it is the strongest
practical argument for closing the corpus-side processing obligation.

## 10. Defect classification and routing

`TOR §5A:98`: "harness defects to WS-E ledger; system-under-test findings to CL
register or the relevant build-stage evidence; corpus defects (a scenario
failing because the corpus is wrong) to the corpus rulings process. **One
defect, one home.**"

### 10.1 The three classes

| Class | What it is | Home |
|---|---|---|
| **Harness defect** | The instrument is wrong: runner, schema, pre-flight, ledger, scoring implementation. The result says nothing about the system under test. | `docs/governance/WS-E_INCIDENTS.md` |
| **System-under-test finding** | The instrument worked and the system behaved as reported. | CL register, or the relevant build-stage evidence |
| **Corpus defect** | The scenario failed because the corpus is wrong — a missing document, a wrong eligibility state, a bad extract. | The corpus rulings process |

### 10.2 Why one defect gets one home

A defect filed in two registers is counted twice and closed once. More
importantly the three registers carry different obligations: a WS-E entry
records an incident about the evidence chain, a CL entry records a change owed
to the system, and a corpus ruling is a governed act against an append-only
store. Filing a corpus defect as a harness defect would put a corpus correction
outside corpus governance entirely — the route by which an append-only store
acquires an unrecorded change.

### 10.3 Classifying is a step, and the default is not "harness"

The classification is not obvious from the failure. A retrieval scenario
returning the wrong documents may be a scoring implementation that computes
recall wrongly (harness), a retriever that ranks badly (system-under-test), or a
corpus in which the expected grounding document is mis-chunked or wrongly
ineligible (corpus).

**Where the classification is genuinely unclear, the finding is recorded as
unclassified with its candidates named**, and classified by ruling. An
unclassified finding is a known state; a finding filed in the wrong register is
a lost one. F1 is the worked example and is so recorded at §12.

### 10.4 What routing does not do

Routing a defect is not closing it, and a routed defect does not by itself
invalidate the run it arose in. Whether a defect of a given class invalidates
prior results is determined by §9.

## 11. Migration-diff comparison semantics (reference)

### 11.1 Reference, not definition

`amendment 3` rules that the semantics are settled per scenario and "live in the
schema so each scenario declares its own comparison rule". The normative
statement is the `migration_diff` definition in
`arcaai/harness/schema/scenario_spec_v0.2.schema.json`; this plan points at it.

The reason is not deference. A rule stated in two places drifts, and the schema
is executable while prose here is not — so a divergence would surface as a
validation failure against a plan a reviewer had already read and believed.

### 11.2 The mechanism as the schema implements it

- `migration_diff` is required on every spec, of either class.
- `comparison` is `bit_identical` or `tolerance`.
- A tolerance comparison requires a tolerance block, itself requiring at minimum
  a metric and a maximum absolute delta.
- A bit-identical comparison carrying a tolerance block is **rejected**: such a
  spec "is a contradiction, and is rejected rather than resolved by precedence."
  Resolving by precedence would silently pick one of two things the author
  asserted.

### 11.3 Why the tolerance must name its cause

Naming the nondeterministic component "is not optional prose: it is how a
reviewer checks that a tolerance was chosen rather than reached for". A bare
delta is unfalsifiable at review; a delta attributed to a named component can be
argued with.

**Finding recorded, not resolved here:** the nondeterminism-source field is
described as the reviewer's check but is **not** in the tolerance block's
required list, which carries only the metric and the maximum absolute delta. A
schema-valid tolerance can therefore omit its cause. The fix is a schema change
and hence a new versioned file; it is queued as a v0.3 candidate. Until then,
this plan requires a tolerance without a stated cause to be treated as
incomplete at review under §5.1's override-reason rule.

### 11.4 Why per-scenario

The schema gives the argument: the pre-migration baseline compares results
across an environment move, "and a result whose comparison rule was never
declared cannot be diffed without inventing one after the fact." An invented
rule is chosen with the diff already in hand — the point at which the choice
stops being a control.

Which scenarios take which rule is a per-scenario authoring decision under the
coverage rule at §2.1. Whether an environment move invalidates prior results is
§9.

### 11.5 Gate consequence

Per `Ruling 4`, the D2.6 pre-migration baseline is a formal hard precondition to
any serving-layer cutover to AWS, and the D3.5 diff report is formally reviewed
before migration is declared complete (rulings record line 48; `TOR §9:139-140`).
The comparison runs at identical spec hashes and corpus snapshot pre- and
post-cutover (`TOR §11`).

D2.6 is a Regime 2 run and requires the ruled Test Plan (`TOR §4:62`). **Until
this plan is ruled, the migration path is blocked at D2.6.**

**(5) What does the D1/D2 ground truth imply here? — answered at §4.**
F1 is a presence question and cannot be answered by gap-detection evidence
