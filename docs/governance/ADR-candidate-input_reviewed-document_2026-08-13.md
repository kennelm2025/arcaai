# ARCHITECTURE REVIEW — Adopting the Orchestration / Memory / Dreaming Principles into the ArcaAI Runtime
*2026-08-09. Chair-commissioned review. Question under review: can the
three principles from the verified conference source (hierarchical
agent orchestration; contextual memory management; dreaming) be
applied to the ArcaAI production runtime on its own stack (LangGraph +
self-hosted open-weight models + BentoML serving), and if so: where
are they stated, where do they insert into the architecture, and where
do they bite the build plan?*

---

## 1. FEASIBILITY VERDICT, PRINCIPLE BY PRINCIPLE

### 1.1 Hierarchical orchestration — FEASIBLE, LOW RISK
The principle (an orchestrator curates; subordinates execute; the
agent that acts never amends its own instructions) is a topology, not
a vendor capability. LangGraph supports it natively: subordinate
agents are graphs (the B6 intake→score→retrieve→package graph is
already one), and the orchestrator is simply another graph — run as a
batch job on its own schedule, never in the serving path. The B6
composition-root discipline (real dependencies constructed at
`scripts/b7_run.py`-style roots, `build_graph` raises rather than
guesses) extends cleanly: subordinate graphs are constructed with
read-only memory handles; the orchestrator graph is constructed with
transcript-set and snapshot handles and NO live-repository write
capability. Nothing here needs anything the stack lacks.

### 1.2 Contextual memory management — FEASIBLE, ALREADY HALF-BUILT
Memory tiers as versioned, hash-pinned artefacts in plain
markdown/structured text is the DEC-0014 corpus-manifest discipline
generalised. The platform already knows how to do this: manifest as
sole governing artefact, append-only eligibility history, two-hash
write preconditions, content hashing in
`arcaai/platform/governance/corpus.py`. Memory management is the same
machinery with a different payload. The genuinely new component is the
CONTEXT ASSEMBLY layer: at subordinate session start, the runtime
resolves which memory version is in force (per tier, per tenant),
verifies its deployment mandate, and injects the content into the
agent's context. That is a loader plus a policy, not a research
problem.

### 1.3 Dreaming — FEASIBLE WITH ONE OPEN RISK
The loop (batch transcript review → evidenced proposed diffs → gate →
versioned commit) is orchestration plus memory plus a batch LLM task —
all available on the stack. The open risk is QUALITY (S17 question F):
whether a self-hosted open-weight model, at economically provisionable
GPU cost, performs the consolidation-review task well enough. This is
the only place the principles touch a genuine capability question, and
the mitigations are known and ordered: (a) NARROW THE TASK — the
orchestrator does structured extraction against defined pattern
schemas (recurring error classes, threshold drift, typology
candidates), not open-ended synthesis; narrow tasks close the gap to
frontier models fastest; (b) SCAFFOLD — multi-pass with
checklist-driven prompts, the dev domain's panel methodology encoded
as pipeline stages; (c) FINE-TUNE IN DEV — on transcripts + accepted/
rejected proposal pairs generated by the Domain-1 /dream rehearsals,
with weights promoted across the firebreak as mandated artefacts.
The ADR already records the resolution order if the pilot disappoints:
narrow the task further; never weaken Rule 8.

## 3. WHERE THEY INSERT INTO THE ARCHITECTURE (the code layer)

1. `arcaai/platform/memory/` — NEW module: tier definitions, versioned
   memory-release loader, context assembly, mandate/admission
   verification at load. Mirrors the retrieval module's shape
   (interface.py store-agnostic; one storage adapter).
2. `arcaai/platform/consolidation/` — NEW module: orchestrator graph,
   transcript-manifest handling, proposal (structured diff) emission,
   proposal-stream instrumentation. Constructed only at a batch
   composition root; no serving-path import (enforceable by the same
   test pattern that fences chromadb imports today).
3. Composition roots — EXTEND: `build_graph` and the batch roots
   refuse to construct without a valid deployment mandate for every
   model/memory artefact they load (the admission check lands here —
   the natural chokepoint the codebase already has; `build_graph`
   already raises rather than guesses, this is one more precondition).
4. Decision-record schema — EXTEND (RAT-02 evolution): add
   memory-version and mandate references to the event metadata so
   every decision states what the system knew and under whose
   authority its components ran. Additive field, minor version bump
   under the existing closed-model discipline.
5. The scorer — UNTOUCHED. Rule 1 is architectural: no import path
   from `verticals/fraud/serving/` into memory modules, asserted by a
   test, exactly as the chromadb fence is asserted today. The 33ms
   P99 budget never meets mutable memory.
6. Audit store — UNCHANGED in shape: consolidation runs, mandate
   events and memory releases are new event types through the
   existing governed_request path (INSERT/SELECT-only grants already
   enforce append-only as a database fact).

## 4. WHERE THE BUILD PLAN SHOULD BE CONCERNED (sequencing + risks)

CHEAP AND EARLY (no new stage; ride existing work):
- Decision-record field extensions (item 3.4) — next time RAT-02
  events are touched; additive.
- Admission-check stub at composition roots (item 3.3) — verify a
  hash-pin records file even before full mandate schema exists; the
  minimal-viable-mandate note in the ADR makes this legitimate.
- The Agentic Topology ADR + memory-pattern DEC — paper, not code;
  draftable as soon as the parent ADR and S17 are ruled.
- Directory scaffolds with interfaces and fencing tests — cheap,
  prevents later architectural drift.

GATED AND SEQUENCED (respect existing gates):
- TENANT ISOLATION DESIGN precedes AWS infrastructure build (already
  a named candidate action; the isolation model must be settled
  before infra is shaped — this is the hardest deadline-like
  dependency in the set).
- CONSOLIDATION ORCHESTRATOR build follows: (a) S16 pilot in
  Domain 1 (/dream rehearsal generating the evidence and the
  fine-tuning data), (b) B9.5 platform extraction (build it once, in
  the extracted platform, not twice), (c) GPU sizing estimate (the
  orchestrator is the heaviest LLM workload the platform will run —
  capacity/cost estimate is a named S17 candidate action and should
  be a precondition of the build decision, not a discovery during
  it).
- WS-T BATTERY additions land with the capability, not after:
  memory-poisoning scenarios, orchestrator-compromise scenarios,
  mandate-verification tests (valid/expired/revoked/tampered), and
  the Rule-8 enforcement tests (CI dependency gate, egress
  assertion) — several of these are testable against stubs before
  the orchestrator exists.
- DXB: the demo narrative gains a beat — the OX dashboard showing a
  proposed memory update arriving at the human gate with its
  evidence — but ONLY after DXB-CHARTER work resumes; no scope creep
  into the current DXB definition.

RISKS TO CARRY OPENLY:
1. Orchestrator model quality at deployable cost (S17-F) — mitigated
   by task-narrowing order; measured by the Domain-1 pilot before any
   production commitment.
2. Context-window economics: open-weight subordinates have tighter
   context budgets than frontier models; memory tiers must ship with
   summarisation discipline (per-tier size budgets stated in the
   Topology ADR) or context assembly will silently crowd out case
   content.
3. Latency creep: the agent layer reading memory is fine; the risk is
   convenience imports drifting memory reads toward the scoring path
   over time. The fence test (3.5) is the control; write it first.
4. Rehearsal debt: the whole plan assumes Domain 1 rehearses the
   architecture (/dream as orchestrator understudy) before Domain 2
   builds it. If S16's pilot is skipped or indefinitely deferred, the
   production build loses its evidence base and its fine-tuning data
   at once — the S16 rulings are therefore on the critical path of a
   PRODUCTION capability, which is worth saying out loud.

## 5. THE SEPARATION PRINCIPLE UNDER EXAMINATION — is the firebreak viable?

The claim under test: unconstrained external AI in development;
mandate-stamped artefacts crossing one way; production that runs
nothing unmandated; a bank that can say "it is my AI and I can vouch
for it" and VERIFY both directions of the firebreak. Honest findings:

### 5.1 Can MLOps actually work across such a firewall? YES — but the
loop changes shape, and the drawback must be owned.
Orthodox MLOps assumes a continuous loop: production telemetry →
monitoring → retraining → redeployment, ideally automated end to end.
The firebreak does not break this loop; it changes its physics from
CONTINUOUS to GOVERNED-BATCH:
- Monitoring runs IN production (it must see live data). What crosses
  back to Domain 1 is derived, minimised artefacts: drift statistics,
  feature/label distributions, performance-vs-outcome aggregates,
  candidate hard cases under the guarded return path. This is the
  standard posture of regulated model estates already — the pattern
  is proven, not novel.
- Retraining, evaluation and champion/challenger comparison happen in
  Domain 1 on returned aggregates plus the bank-data training zone
  (5.3); winners cross as newly mandated artefacts.
- THE HONEST DRAWBACK: loop latency equals release cadence, not
  minutes. For fraud this bites exactly where S17 question A says it
  does — emerging attack waves. Mitigation, to be designed as a
  first-class release class: a POLICY FAST LANE — thresholds, rules
  and list updates within PRE-VALIDATED bounds move on an expedited
  governed path (hours), while model weights move on the standard
  path (days/weeks). The bounds themselves are validated slowly;
  movement within them is fast. Cadence becomes a designed property
  per artefact class, not a single speed.

### 5.2 Reproducibility across the firebreak — the skew problem.
The mandate binds WHAT crosses; it does not by itself guarantee the
artefact BEHAVES identically in production (training/serving skew,
environment drift). Controls, two of which the house already
practises: (a) pinned runtime images promoted with the same mandate
discipline as models; (b) PARITY TESTS — the scorer already
re-states the margin→Platt map and parity-checks it against the
offline pipeline (`test_serving.py`); this pattern generalises to
every promoted model; (c) the regression harness diff as acceptance
evidence — already the pre-AWS migration plan. The firewall works
because parity is TESTED at the gate, never assumed.

### 5.3 The training-data question — Domain 1 has two zones.
"Unconstrained external AI" and "customer data discipline" coexist
because the constraint attaches to DATA, not tools. Stated precisely,
Domain 1 subdivides:
- FRONTIER ZONE: any external model, any vendor — operating on
  synthetic data (the corpus), public data, and authorised-minimised
  exports only. This is where capability is driven out.
- BANK-DATA TRAINING ZONE: where models meet real customer data for
  the upskilling stage — in-perimeter tooling, or external processors
  ONLY under explicit authorised arrangements (DPAs, private
  endpoints, minimisation). The bank chooses its own comfort point;
  the framework does not force customer data toward any external
  processor.
The zones share the Domain-1 governance register and audit trail;
artefacts from both cross the same firebreak with the same mandates.
[AMENDMENT CANDIDATE for ADR v0.2: the two-zone refinement and the
policy fast lane — the frozen v0.1 implies but does not state them.]

### 5.4 Emergency response — what happens at 2am? 
No hotfixing in production is a feature, not a gap, IF the
alternatives are fast: mandate REVOCATION stops a misbehaving
component at its next admission check; ROLLBACK re-admits the
previous known-good mandated artefact; the policy fast lane covers
containment actions (tighten a threshold, add to a blocklist) within
pre-validated bounds. The incident story to a regulator becomes
"we degraded to the last validated state in minutes and shipped the
fix through the gate" — stronger than "we patched live".

### 5.5 Verifiability — can the bank PROVE no leakage, both ways?
This is the load-bearing requirement and it is achievable with
bank-runnable checks, none dependent on ArcaAI's word:
INBOUND (nothing unmandated runs):
- Reconcile: hash of every deployed artefact == hash in a valid
  mandate == hash in the promotion record. A three-way match the
  bank's audit team can script.
- CI gate evidence: dependency audit of production build artefacts —
  zero external-AI endpoints/SDKs/credentials — as a retained,
  signed CI output.
- STANDING CANARY (answers S17 question G affirmatively): a
  production-resident test component periodically attempts an
  external AI call and an unmandated load; both MUST fail, and the
  failures are logged as positive evidence. The guardrail is proven
  continuously, not asserted once.
OUTBOUND (no leakage of intelligent assets or customer data):
- Egress default-deny with a short, named allow-list (scheme
  endpoints, JWKS — non-AI, cacheable); the firewall config is the
  bank's own and readable.
- Egress logs: every outbound flow enumerable; the guarded-return-
  path artefacts are a finite, reviewable set.
- Periodic CONTAINMENT ATTESTATION: an auto-generated evidence pack
  (egress summary, mandate ledger, canary results, CI gate outputs)
  — the "I can vouch for it" statement rendered as a recurring,
  auditable artefact a CRO can table at board risk committee.

### 5.6 Drawbacks owned honestly (the cost of the principle)
1. Release cadence slower than an ungoverned SaaS competitor —
   answered by the fast lane and by the market: the buyer is
   regulated, and the competitor's speed is precisely what fails a
   skilled-person review.
2. Environment duplication cost (dev estate + prod estate + the
   firebreak machinery) — real, but the framework ships the pipeline
   so the smallest bank does not build it from scratch; this is part
   of what ArcaAI IS.
3. Discipline overhead for a two-person team — the thesis accepts
   this bet explicitly: the framework + frontier-model leverage in
   Domain 1 must make the governed path CHEAPER than the ungoverned
   one, or the thesis fails. The Domain-1 harness (this project's
   own practice) is the existence proof under construction.
4. Shadow-path risk — the standing threat is not the architecture
   but a human opening a convenience hole. Controls: firewall/CI
   config as code under the same review gates; the canary catches a
   hole that reaches production; WS-E-style incident discipline
   catches the rest.
5. Skills gap at small banks — the process must be genuinely
   turnkey; every place the framework demands judgement instead of
   following a checklist is a sale-blocker to quantify during
   discovery conversations.

### 5.7 Finding on the separation principle
VIABLE. The firebreak is a cadence-and-cost trade, not a feasibility
barrier: the MLOps loop survives as a governed batch loop with a
designed fast lane; reproducibility is a tested property with house
precedent; the data question resolves by zoning Domain 1; emergencies
are answered by revocation + rollback + fast lane; and — decisively —
both directions of the firebreak are INDEPENDENTLY VERIFIABLE by the
bank through reconciliation, canary, egress evidence and a recurring
containment attestation. The principle's costs are real, named above,
and are exactly the costs the target buyer is already obliged to pay
in some form; the framework's job is to make paying them cheap.

## 6. VERDICT

Yes — all three principles transfer to the ArcaAI runtime without any
dependency on the source's vendor stack, because they are patterns
(topology, artefact discipline, batch loop) and the stack already
practises their nearest ancestors (LangGraph graphs, DEC-0014
manifests, RAT-02 instrumentation, composition-root discipline). The
statement layer is two ADRs + two CLs + one small DEC; the code layer
is two new platform modules, two extensions, one fence; the build-plan
exposure concentrates in three places: tenant isolation before AWS,
GPU economics before the orchestrator build, and the S16 pilot as the
evidence gate for everything downstream. The single open capability
risk (orchestrator quality on open weights) has a defined mitigation
order and a defined measurement point, and the ADR already rules that
its worst case narrows the task rather than weakening the firebreak.
The separation principle itself (section 5) is found VIABLE: a
governed-batch MLOps loop with a policy fast lane, tested parity, a
two-zone development domain, revocation-based incident response, and
bank-runnable verification of both firebreak directions. Two
amendment candidates carry to ADR v0.2 (two-zone Domain 1; policy
fast lane as a release class), and the standing canary answers S17
question G in the affirmative before that panel convenes.
